### Runtime status

```ts
interface RuntimeStatusResponse {
  observed_at: string
  summary: "PENDING" | "AVAILABLE" | "INITIALIZING" |
    "RESTRICTED" | "UNAVAILABLE" | "STALE"
  components: {
    api: RuntimeComponent
    database: RuntimeComponent
    worker: RuntimeComponent
  }
  base: RuntimeBase
}

interface RuntimeComponent {
  state: "PENDING" | "AVAILABLE" | "INITIALIZING" | "RESTRICTED" |
    "UNAVAILABLE" | "STALE" | "IDLE" | "RUNNING"
  schema_current: boolean | null
  last_seen_at: string | null
}

interface RuntimeBase {
  state: "EMPTY" | "AWAITING_OPERATOR" | "INITIALIZING" |
    "DOWNLOADING" | "PROCESSING" | "LOADING" | "VALIDATING" |
    "READY" | "FAILED" | "UNAVAILABLE" | null
  active_competence: string | null
  available_competence: string | null
  preparing_competence: string | null
  action_required: string | null
  current_stage: string | null
  progress: Record<string, unknown> | null
}
```

Na resposta 200, a API é `AVAILABLE`; Banco é `AVAILABLE` ou `UNAVAILABLE`; Worker é `IDLE`, `RUNNING`, `STALE` ou `UNAVAILABLE`. `summary=AVAILABLE` somente ocorre com `base.state=READY`.

### Preflight

O DTO real contém `source`, `competence`, `file_count`, `shard_count`, `download_bytes`, `reusable_bytes`, `remaining_download_bytes`, `free_bytes`, `workspace_estimate_bytes`, `database_ready`, `schema_current`, `worker_available`, `lock_available`, `blockers`, `can_start` e `observed_at`.

Os campos `download_bytes`, `remaining_download_bytes`, `free_bytes` e `workspace_estimate_bytes` são nullable. Os blockers atuais são:

```text

database_unavailable
worker_unavailable
base_already_ready
base_initializing
lifecycle_unavailable
job_active
lock_unavailable
workspace_insufficient
```

### Bootstrap e health

`POST /api/v1/base/bootstrap` recebe `{ "competence": "latest" }`. A resposta contém apenas `job_id`, `competence`, `status` e `replayed`. O `job_id` não é necessário para polling ou persistência no navegador.

`GET /health/live` retorna `{ "status": "ok", "service": "sentinel-api" }`. `GET /health/ready` retorna 503 público com `database_unavailable`, `base_setup_required`, `base_initializing` ou `base_unavailable` enquanto a base não estiver apta.

## D. Gaps issue × backend

| Item | Classificação | Evidência e decisão |
| --- | --- | --- |
| Código/mensagem de `FAILED` | **SUPORTADO** | `last_failure_code` e `last_failure_message` agora são publicados, sanitizados e nullable. |
| Etapa de `FAILED` | **SUPORTADO** | `current_stage` preserva o último estágio persistido antes da falha; `progress=null`. |
| Retry em `FAILED` | **SUPORTADO** | Preflight aceita `FAILED`; `can_start=true` habilita visualmente, e o POST é a autoridade final. |
| Download agregado da competência | **AJUSTE DE COPY** | Runtime contém bytes somente do arquivo corrente. |
| Processamento por stage/shard | **SUPORTADO** | Há stage, shard atual/total e completed; total de unidades pode ser nulo. |
| Construção da base útil | **SUPORTADO condicionalmente** | Só é distinguível em `PROCESSING` com `stage=BUILD_BASE_UTIL`. |
| Checks de validação | **AJUSTE DE COPY** | Há `VALIDATING` e `VALIDATE_MATERIALIZATION`, mas não índices de checks. |
| ETA | **SUPORTADO por omissão** | Não existe contrato de ETA. |

### Gap backend obrigatório

**A UI não possui hoje contrato público para mostrar failure_code/message.**

A menor extensão backend é acrescentar `last_failure_code: string | null` e `last_failure_message: string | null` a `RuntimeBase` e serializá-los no helper `_base()` de `sentinel_api/routers/runtime.py`. Os dados já são persistidos e sanitizados pelo worker.

Sem esse ajuste, a #27 não cumpre integralmente o cenário `FAILED`; pode apenas apresentar falha genérica e retry condicionado ao preflight.

## F. Polling

```text
mount / aba visível / retry manual / POST concluído
→ consulta runtime imediata

resposta válida
├── duas respostas consecutivas saudáveis: 60 s
└── qualquer outro caso: 15 s

aba oculta → abortar request e cancelar agendamento
aba visível → consulta imediata
unmount → abortar, invalidar geração e cancelar agendamento
```

Regras obrigatórias:

- `setTimeout` encadeado; nunca `setInterval`.
- `AbortController` e generation id por rodada.
- Nunca sobrepor rodadas.
- Respostas antigas são ignoradas.
- Snapshot frontend stale somente após 120 s desde a última resposta runtime válida.
- `worker=STALE` é dado backend e não pode ser confundido com snapshot frontend stale.

Falha de transporte sem snapshot válido mostra “Sistema indisponível — sem confirmação” e os três componentes como desconhecidos. Com snapshot válido recente, preserva a última confirmação, mostra restrição e retry. Aos 120 s sem confirmação, apresenta “Dados desatualizados” e não mantém componentes como confirmados.

## H. Onboarding e progresso

### Onboarding

Mostrar competência, arquivos, download total quando conhecido, bytes reutilizáveis, download restante quando conhecido, espaço livre, estimativa de processamento apenas quando informada e horário de observação. `shard_count` é secundário e não substitui arquivos.

Usar formatter binário local (`B`, `KiB`, `MiB`, `GiB`); `null` nunca vira zero. `workspace_estimate_bytes=null` deve aparecer como “não calculado”.

Whitelist de blockers:

```text
source_unavailable      → Não foi possível confirmar a publicação disponível.
workspace_unavailable   → O espaço de trabalho do servidor não está disponível.
database_unavailable    → O banco do Sentinel está indisponível.
worker_unavailable      → O worker de preparação não está disponível.
base_already_ready      → A base já está preparada.
base_initializing       → Já existe uma preparação em andamento.
lifecycle_unavailable   → O estado operacional não está disponível.
job_active              → Já existe uma preparação em andamento.
lock_unavailable        → A preparação está temporariamente ocupada.
workspace_insufficient  → Não há espaço livre suficiente para esta preparação.
unknown                 → A preparação não está disponível no momento.
```

O botão só aparece quando `can_start=true`. Durante o POST fica desabilitado, com estado busy, para impedir duplo clique.

### Confirmação

```text
Preparar base
→ diálogo acessível
→ competência, download conhecido ou não informado, bytes reutilizáveis
→ aviso de continuidade no servidor
→ Cancelar / Preparar base
```

O diálogo exige `role="dialog"`, `aria-modal`, `aria-labelledby`, `aria-describedby`, foco inicial em Cancelar, Escape, trap de foco e retorno ao botão de origem. Depois de 200/202, a UI descarta o job e força refresh runtime imediato.

### Progresso efetivamente publicado

| Estado | Evidência apresentada |
| --- | --- |
| `INITIALIZING` / `DISCOVERY` | Descoberta em andamento |
| `DOWNLOADING` | arquivo atual/total; bytes do arquivo corrente |
| `PROCESSING` | stage, shard atual/total, completed se existente |
| `PROCESSING` + `BUILD_BASE_UTIL` | Construção da base útil |
| `LOADING` | linhas somente quando completed e total forem válidos |
| `VALIDATING` | Validação sem percentual |
| `READY` | Concluído |
| `FAILED` | Código/mensagem somente após o ajuste backend |

Não há percentual global, ETA, check count, nome de arquivo público nem bytes acumulados da competência. Na transição para READY, anunciar conclusão, montar Discovery vazio e não disparar busca. Após reset para `AWAITING_OPERATOR`, desmontar Discovery sem manter resultados antigos.
